How NANO QUEST
works

A Mario-style platformer built out of logic gates. There's no processor, no program and no stored picture. Every pixel is worked out at the moment the HDMI cable needs it, 25.2 million times a second, and the game itself runs in the gap between two frames.

World 1-1

No CPU: five circuits side by side

An FPGA is a chip full of small, uncommitted building blocks: about 8,640 four-input lookup tables (each can be any logic function of 4 bits), 6,480 flip-flops that each remember one bit, adders, and 26 blocks of on-chip RAM. A design written in Verilog describes how to wire those blocks together. When the chip powers up it loads that wiring from flash, and from then on it is the circuit.

There's no instruction stream and no "main loop". NANO QUEST is five circuits wired side by side, all ticking on the same 25.2 MHz clock and all doing their work at once:

  • dvi_tx generates the video timing, asks for one pixel per clock, and turns the colours it gets back into HDMI signals.
  • plat_render works out the colour of each pixel from the level, the sprites, the text and the palette, with no memory of what it drew before.
  • plat_game holds the world: Nano, the slimes, the score and the timer. It advances everything by one frame each time dvi_tx says a picture has finished.
  • plat_map is the level itself, 256 × 16 tile numbers in RAM. The renderer reads it and the game reads and writes it at the same time.
  • plat_sfx plays sound effects as square waves on one pin.

All of it is in platformer.v (about 1,000 lines) and the shared HDMI core in hdmi/common. The rest of this page walks through each piece with interactive versions built from the game's real data.

World 1-2

Racing the beam

A 640×480 picture at 60 Hz is sent as a stream: left to right along each line, top to bottom, one pixel per tick of a 25.2 MHz clock. Each line is actually 800 clocks long and each frame 525 lines tall. The extra time is blanking, left over from CRTs that needed time to swing the electron beam back, and it's where the sync pulses go.

The usual way to make a picture is to draw it into a frame buffer in memory and have the video hardware read it out. This chip has 26 blocks of 18 Kbit RAM, about 479,000 bits in all. A 320×240 frame of 6-bit colour numbers is 460,800 bits, 96% of it, leaving nothing for the art or the level.

So NANO QUEST does what the Atari 2600 did and races the beam. dvi_tx announces which pixel it's about to send, (x, y), and the renderer has to hand back that pixel's colour exactly 3 clocks later. Nothing is stored between frames: the picture exists only as it goes down the cable.

This design has a neat side effect: the game only changes the world during vertical blanking, when nothing is being drawn. Every frame is drawn from one consistent state, with no tearing and no double buffering.

World 1-3

From colours to HDMI wires

The Tang Nano 9K's HDMI socket is wired straight to FPGA pins, with no video chip in between, so the FPGA has to produce the signal itself. HDMI is backwards compatible with DVI, and plain DVI is all this needs: three data wire pairs (red, green and blue) and a clock pair.

Why 10 bits for an 8-bit colour?

At 252 Mbit/s over a cheap cable, the receiver has to recover the bits from the edges it sees, and the signal can't drift towards all-ones or all-zeros. TMDS (transition-minimised differential signalling) handles both in two steps:

  1. Fewer transitions. Each bit is XORed with the previous output bit, or XNORed if the byte has lots of ones. Whichever gives fewer changes wins, and bit 8 records the choice.
  2. DC balance. The encoder keeps a running count of ones minus zeros sent so far. If the next word would push that count further from zero, it inverts the word and sets bit 9 to say so.

During blanking the encoder sends one of four special control words instead. They carry the horizontal and vertical sync pulses on the blue channel. Try it with the game's own colours:

World 1-4

Art is just numbers

Nothing is drawn inside the FPGA. A Python script, platformer_gen.py, makes all the graphics, text and the level, and writes them as hex files. When the design is built, those files become the initial contents of the chip's block RAMs.

The characters are typed in by hand as grids of letters, one letter per pixel and one colour per letter. Hover over either side to see how they match:

The script then packs everything into tables. Tiles are 16×16 at 4 bits per pixel with their own 16-colour palette. Clouds, hills and bushes are drawn as large shapes and cut into tiles, and simple things like bricks and pipes are drawn from rules. Here's everything the renderer has to work with:

Animation without moving anything

Spinning coins and shimmering ? blocks don't need any game logic. The level stores a tile id like "34 = ? block". The renderer looks up the artwork through a small slot table indexed by the tile id and two bits of the frame counter, so the same id shows different artwork as time passes:

World 2-1

The level is a grid of tile numbers

The course is a 256 × 16 grid of tile ids, 6 bits each, in a RAM called plat_map. The script builds it from commands like "pipe of height 4 at column 46" or "#M#?# at row 9". Only the ids are stored; the artwork is looked up while the picture is drawn.

The tile ids are numbered so the game can tell solid from background by checking a single bit: every id from 32 up is solid. The whole collision rule in hardware is solid = t[5], one wire with no comparison needed. Drag the minimap or the view to scroll, and try the overlays:

World 2-2

Drawing one pixel in 3 clocks

Block RAM gives its answer one clock after you give it an address, and some lookups depend on the result of another: you need the tile id before you can fetch the tile's pixel. So the renderer is a pipeline. It's split into stages with a register between each, like an assembly line. Each clock, every pixel moves one stage along and a new one comes in:

  1. Clock 0, addresses. Halve x and y (each game pixel is 2×2 on screen), add the camera to get the world position wx, and form the map address {ly[7:4], wx[11:4]}. Test whether any sprite covers this pixel, and find which text string, if any, sits on this row.
  2. Clock 1, first reads. The map returns the tile id. The sprite memory returns one pixel for Nano and one for the first other sprite that covers this point. The text memory returns a character code.
  3. Clock 2, second reads. The tile id and animation bits choose a slot, and the slot plus the position inside the tile give a 4-bit tile pixel. Placeholder characters become live score digits, and the font gives a row of 8 bits.
  4. Clock 3, pick the colour. Take the top non-transparent layer: text, then Nano, then other sprites, then the logo, then tiles. The palette turns that into 24-bit RGB.

The sprite test: one subtraction, no comparisons

Every pixel has to ask eleven sprites "do you cover me?". Written the obvious way that's four comparisons per sprite, and on this chip every comparison costs a chain of adder cells. The renderer uses a cheaper trick instead: subtract the sprite's corner from the pixel's position in 12-bit arithmetic, then check that the top 8 bits are all zero.

The sprite memory has two read ports, so each pixel can fetch two sprite pixels per clock: one for Nano, and one for the first other sprite in a fixed order (coin pop, mushroom, slimes, brick chunks). If two slimes overlap, only the first shows in the overlap. That's a hardware limit, much like the NES's eight sprites per line, and in play you rarely notice it.

World 2-3

Sprites, big Nano and the mushroom

A sprite is just 27 bits of game state: a visible flag, a frame number, and a y and x position. The game packs Nano, four slimes, four brick chunks, the coin pop and the mushroom into wires that run to the renderer. Moving a sprite means changing a number.

Big Nano is 32 pixels tall but the sprite memory holds 16×16 frames, so big poses are stored as pairs from frame 16. The renderer uses a 32-row box test for the hero and picks the frame with one bit of the row inside the box: hero_fr = {1, pose, dy[4]}. Top half, bottom half, no extra memory port.

The mushroom rises out of its block like in the classics: it's drawn behind the block while it emerges. There's no layer system to do that, so the game sets mush_clip to the top edge of the block and the renderer hides mushroom pixels below that line. Turn the clip off to see what it's hiding:

World 3-1

The game runs between frames

A frame lasts 420,000 clocks. When the picture reaches the bottom of the screen, dvi_tx sends a one-clock frame tick, and the next 36,000 clocks are vertical blanking, with nothing drawn. The game needs about 41 of them:

Why not do it all at once? Collisions need the level map: "is the tile ahead of Nano's feet solid?" The map has one port for the game, and it answers one question per clock, two clocks after you ask. So the game is written as a step machine, one small step per clock, each one asking the map a question or using an answer that just arrived. Step through one real frame: big Nano is falling and running right, towards a block and a coin:

Checking three points along the leading edge matters. Big Nano is 28 pixels tall, so a one-tile block can slip between the head and feet probes. That's why there's a third, middle probe at +14. The game also moves Nano first and asks questions afterwards. It guesses the new position, and if a probe lands inside something solid, it snaps back to the tile boundary: {xr[11:4], 4'd0} − 12. Snapping is just clearing the low 4 bits.

World 3-2

Physics in sixteenths of a pixel

Whole pixels are too coarse for good movement: the slowest speed would be 60 pixels a second. So every position and speed is fixed-point, counted in 1/16ths of a pixel. The renderer just drops the low 4 bits. The whole feel of the game comes down to a handful of constants:

ConstantValueMeaning
ACC / DEC2 / 4speed up 1/8 px per frame each frame while S2 is held; slow down twice as fast
VMAX36top running speed: 2.25 px per frame, 135 px per second
JUMP_V84launch speed: 5.25 px per frame upwards
GRAV8gravity: 0.5 px per frame, every frame
GRAV_HOLD3gravity while S1 is held and Nano is still rising
VY_MAX96fastest fall: 6 px per frame

GRAV_HOLD is the secret of the variable-height jump: while you hold the button on the way up, gravity is less than half as strong. Let go and it snaps back to normal. That's why a tap gives a hop and a hold gives a leap. Try it:

A tap rises about 28 px, less than two tiles. A full hold rises about 71 px, four and a half tiles, and stays in the air twice as long. Two more details from the Verilog:

  • Jumps need a fresh press. The game remembers last frame's button (jump_prev) and only jumps on a press, so holding S1 doesn't bunny-hop.
  • Standing is falling a little. Gravity pulls a standing Nano half a pixel into the floor every frame, and the floor check pulls it back to the tile's top edge. Standing and landing are the same code.

World 3-3

A level you can break

The level map is live memory with two ports. Block RAM on this chip can serve two addresses per clock, so the renderer and the game never wait for each other:

Breaking a brick works the same way. When a head-bump reaches step 9 and the tile above is a brick, the game writes T_SKY into the map, adds 50 points and launches four chunks, one from each corner. Each chunk is its own small physics object: ±1.25 px per frame sideways, thrown up at 4.5 or 2.5 px per frame, with gravity of 6/16.

The first version had a bug that showed up on the real monitor: the chunks bounced. Each chunk's vertical speed was an 8-bit signed number, and nothing stopped it growing. About half a second after the break it passed +127 and wrapped round to about −125, and the chunk shot back up, sometimes more than once. World 3-4

Sound from one pin

The sound hardware is a counter and a flip-flop. The counter counts pixel clocks, and when it reaches the note's half period it resets and flips pin 25. That makes a square wave at 25.2 MHz ÷ (2 × (half + 1)), the same kind of raw buzz as the NES's pulse channels. A small piezo buzzer between pin 25 and ground plays it.

Each effect is a table of up to four notes, each with a half period and a length in frames. Click to hear them. Your browser plays the same square waves at the same pitches and lengths:

World 4-1

Testing without seeing the screen

NANO QUEST was written by Claude, an AI, working over SSH. The board is plugged into a Linux machine, and the monitor sits on a desk Claude can't see. So nearly everything was proven in simulation before it went near the chip. Icarus Verilog runs the actual platformer.v clock by clock.

A bot plays the game

plat_bot.vh is a player written in the testbench. It reads the game's state and the level map, the same things a person sees on screen, and presses the buttons: always run, and jump (holding for a high jump) when there's a wall, a pit or a slime ahead. It lets go of S1 on landing so the next jump is a fresh press. The test first steers Nano under the first mushroom block and waits for the mushroom, then plays World 1-1 as big Nano and World 1-2 small. It passes only if both worlds are cleared.

After every simulated frame the testbench checks:

  • Nano is never inside a solid tile.
  • Nano never starts a jump while in the air.
  • Nano never loses the ground while standing on something.
  • A smashed brick is really gone from the level RAM.
  • Growing keeps Nano's feet where they were, and shrinking only happens to big Nano and never costs a life.
  • The mushroom appears exactly once and gets eaten.

In the latest run the mushroom is eaten on frame 352 and both worlds are cleared with no deaths.

Bugs the tests caught

mid-air jumpDouble jumps

The on_ground flag was only updated while falling. On the way up it kept its old value, 1, so a second press in mid-air counted as a jump from the ground and could launch Nano off the top of the screen. The fix is the on_ground <= 1'b0 in the rising branch of step 7 above.

ground checkAirborne every other frame

The floor probe first looked at Nano's own bottom row of pixels instead of the row just below the feet. Gravity pulls a standing Nano down half a pixel per frame, so the whole-pixel position only changes every other frame. On alternate frames the probe saw sky, and Nano briefly counted as falling. That would have made jumps work only half the time.

8-bit overflowBouncing brick chunks

The chunk speed wrap in World 3-3. That one got past the tests and was spotted on the real monitor. The fix was a speed cap, and the page's brick demo shows both versions.

bit widthsA sprite word that didn't fit

The mushroom's sprite word is 27 bits: visible, frame, 10-bit y, 12-bit x. The first version put a 16-bit y into it. Verilog silently keeps the low 27 bits of a too-wide value, which would have lost the visible flag and frame number. It was fixed by taking dyp[9:0].

bit widthsA bump that beeped

The bump sound's half period was first 84,000, which doesn't fit in the 16-bit field. It would have wrapped to 18,464, a high 680 Hz beep instead of a low thud. Now it's 63,000, a 200 Hz thump.

From Verilog to the chip

The build uses an entirely open-source toolchain, with no vendor IDE:

Where it ended up on the GW1NR-9:

nextpnr reports the design would run at up to 36.3 MHz, and it only needs 25.2, so there's room for more worlds and enemies. A few lessons from getting there:

  • Comparisons are expensive. On this chip, each < or > between two numbers becomes a chain of adder cells. That's why adder cells are the most used logic resource, and why the renderer uses bit tests like the sprite trick above wherever it can.
  • Keep scores in decimal. The score, coins and timer are stored as BCD, one 4-bit nibble per decimal digit. The HUD can then show a digit by picking a nibble, with no division hardware at all.
  • Check the clock routing. The 126 MHz clock must reach the divider over a dedicated route, or the serialisers' clocks can drift out of line and the monitor shows nothing. The placer's random seed decides this, so the Makefile greps nextpnr's log and fails the build if the route wasn't used.
